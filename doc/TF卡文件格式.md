# TF 卡文件格式约定

本文件是准备素材（图片、音乐）与编写 FPGA 解析逻辑的共同依据。

---

## 0. 素材与产物的目录布局

```
F:\桌面\hdmi_fpga_video\          ← 工程根目录
├─ 素材\                          ← 你自己建，原始素材放这里，命名随意
│   ├─ 图片\   01_风景.jpg  02_产品.png  …
│   └─ 音乐\   01_风景.mp3  02_产品.wav   …
├─ bmp_out\                       ← prepare_images.py 生成（自动创建）
│      00_01_风景.bmp … 07_…
├─ aud_out\                       ← prepare_audio.py 生成（自动创建）
│      00_01_风景.aud … 07_…
├─ tools\                         三个脚本
├─ rtl\  sim\  con\  prj\  doc\
```

要点：

* **输入素材放哪都行**，路径由你在命令行给出；上面只是推荐位置。
* **产物默认落在工程根目录下**的 `bmp_out` / `aud_out`，与你在哪个目录执行命令无关
  （脚本按自身位置解析工程根，不用相对路径）。
* `write_card.py` 的 `-i` / `-a` 默认就指向这两个目录，所以常规流程不用记路径。
  若用 `-o` 改了输出位置，记得给写卡工具也加对应的 `-i` / `-a`。

### 不想敲命令行：直接双击

`prepare_images.py` / `prepare_audio.py` 支持双击运行（不带任何参数时）：

1. 第一次双击：自动建好 `素材\图片` 或 `素材\音乐`，并提示把素材复制进去
2. 把素材复制进去
3. 再双击一次：自动全部转换，结果落在 `bmp_out` / `aud_out`

顺序按**文件名排序**，所以要调整播放顺序就改文件名。
脚本结束前会停住等你按回车，不会一闪而过。

## 1. 卡的整体要求

| 项 | 要求 |
|---|---|
| 容量 | 至少 1 GB，建议 8 GB 以上（音轨占地方大） |
| 文件系统 | FAT32（MBR 分区表）。FPGA 按扇区顺序扫描，不解析目录项 |
| 放置位置 | 根目录，文件名以数字开头可加快扫描命中 |
| 写入方式 | 必须用 `tools/write_card.py` 顺序写入，见第 5 节 |

> FPGA 不解析文件系统，而是在卷内逐个扇区扫描文件头签名。因此**直接在电脑上删除
> 文件是无效的**——旧文件的物理数据仍留在扇区里会被扫到。这不是缺陷，是官方样例
> 既定的读取方式，我们用同一套流程。

### 1.1 第 0 扇区（MBR）：板上先核对什么

M3 的验收就是"把 LBA0 读出来"，M4 起才进 FAT32 解析。当前实现看这些偏移：

| 偏移 | 长度 | 字段 | 用途 |
|---|---|---|---|
| 446 | 1 | 分区 1 状态字节 | 只记录，不参与判错 |
| 450 | 1 | 分区 1 类型 | `0x0B` / `0x0C` 是 FAT32；读到 0 视为"没有分区表" |
| 454 | 4 | 分区 1 起始 LBA | 小端；M4 定位根目录时要加上它 |
| 458 | 4 | 分区 1 扇区数 | 小端；容量 = **向上取整(扇区数 / 2²¹)** GiB，显示在数码管 d3 d2（十六进制，`10` 表示 16 GiB） |
| 510 | 2 | 尾部签名 `55 AA` | 必须命中，否则判为读扇区失败（d4=`F`、d2=5） |

Windows 给 SD 卡格式化一定会建 MBR 分区表，所以正常情况这些字段都可解析。
若卡是"超级软盘"格式（没有分区表），签名仍在 510/511，但 450 处是引导代码，
此时 FPGA 显示 `A 00`：扇区读通了，只是没有可用的容量信息——M4 解析要按这个
情况回退（按 VBR 直接当卷首处理）。

### 1.2 扫描规则（M4 已实现）

找图片的方式：从 MBR 给出的分区起始 LBA 开始，逐个扇区只看扇区开头的字节。

| 项 | 规则 |
|---|---|
| 命中条件 | 扇区首两字节是 `BM` |
| 头部校验 | 长度 ≥ 921654（要覆盖全部像素）、像素数据偏移 = 54、宽 640、高 480、位深 24、非压缩 |
| 记录内容 | 起始 LBA + 文件长度，最多 8 条 |
| 跳过 | 记下一张后按头部声明的长度直接跳到下一张；`MMAU` 音轨也按头部长度跳过 |
| 停止条件 | 连续 16 MB 没找到新图片 / 扫描预算 100 MB / 记满 8 张 |

由此推出的写卡约束：

* **每个图片文件的起始扇区首字节必须是 `BM`**，也就是文件要从扇区边界开始，
  前面不能垫别的数据。用文件系统写入天然满足（FAT32 下文件从簇边界开始）。
* 图片必须是 640×480 / 24 位 / 非压缩 / 数据偏移 54，`prepare_images.py` 的输出
  正好符合。
* 卡上不能留旧图片的物理数据（把文件删掉不算清干净），否则会被当成新图扫到——
  这正是 `write_card.py` 要覆写一遍可用空间的原因。
* 扫描不看目录项，所以文件名和所在目录都不影响识别，只影响 `write_card.py` 的
  写入顺序，也就是最终扫描到的顺序。

## 2. 图片格式

| 项 | 值 |
|---|---|
| 格式 | Windows BMP，BITMAPINFOHEADER（DIB 头 40 字节） |
| 分辨率 | 640 × 480 |
| 位深 | 24 位 RGB |
| 压缩 | 无（`biCompression = 0`） |
| 像素数据偏移 | 54 |
| 行字节数 | 1920（640 × 3，恰好 4 字节对齐，**无行补位**） |
| 行存储顺序 | 自下而上（`biHeight` 为正），显示时需垂直翻转 |
| 单张文件 | 921,654 字节 = 1,800.1 个扇区 |
| 识别签名 | 偏移 0 处的 `BM`，并核对宽高 / 位深 / 压缩方式 |

用 `tools/prepare_images.py` 生成，它会打印实际头字段供核对。

---

## 3. 音轨容器（`*.aud`）

自定容器，**头部固定 512 字节**，因此 PCM 数据总是扇区对齐，FPGA 连续流式读取时
不需要任何字节相位记账。

### 3.1 头部字段

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0x000 | 4 | 魔数 | ASCII `MMAU` |
| 0x004 | 2 | 版本 | 1 |
| 0x006 | 2 | **场景编号** | 该音轨属于第几张图（从 0 开始） |
| 0x008 | 4 | 采样率 | 48000 |
| 0x00C | 2 | 通道数 | 2（立体声） |
| 0x00E | 2 | 位深 | 16 |
| 0x010 | 4 | 采样帧数 | 每声道的采样数 |
| 0x014 | 4 | 数据字节数 | = 帧数 × 通道数 × 位深/8 |
| 0x018 | 4 | 数据偏移 | 512 |
| 0x01C | 4 | 保留 | 0 |
| 0x020~0x1FF | — | 保留 | 全 0 |
| 0x200 | — | PCM 数据 | 交织 L/R，小端有符号 16 位 |

文件总长度补齐到 512 字节的整数倍。

### 3.2 为什么不用 WAV

WAV 头部只有 44 字节，数据起始位置不是扇区对齐的，而且 chunk 长度可能为奇数。
FPGA 从 SPI 连续读 PCM 时，需要维护字节/半字相位；把数据固定在 512 字节边界之后
可以把这部分逻辑完全省掉。代价是文件不能直接用播放器打开——`tools/prepare_audio.py`
也支持反向核对，见第 4 节。

### 3.3 参数取值

| 项 | 值 | 由来 |
|---|---|---|
| 采样率 | 48 kHz | 赛题要求 |
| 通道 | 2 | HDMI 标准立体声 |
| 位深 | 16 | 兼顾质量与带宽 |
| 数据率 | 1.536 Mbit/s | 48k × 2 × 16 |
| SPI 需求 | 约 1 个扇区 / 2.7 ms | 25 MHz SPI 下占用不足 8% |

## 4. 配对规则

音轨头里的**场景编号**决定它属于哪张图，不依赖文件名，也不依赖扫描顺序。
图片按扫描到的先后顺序编号（0 开始）。

准备素材时让 `prepare_images.py` 与 `prepare_audio.py` 用同样的顺序即可：

```
python tools/prepare_images.py 素材/图片 -o bmp_out
python tools/prepare_audio.py  素材/音乐 -o aud_out --start-scene 0
```

两个脚本都会按输入顺序给文件名加两位序号前缀，便于人工核对。

## 5. 写卡流程

```
python tools/write_card.py --no-audio --dry-run   # 先看计划（盘符默认 G:，不动卡）
python tools/write_card.py --no-audio             # 确认无误再写：只写图片
python tools/write_card.py --dry-run              # 图 + 音轨都写（M7 之后）
python tools/write_card.py -n 3 --no-audio        # 只有 3 张图时
```

`--no-audio` 用于图像通路调试阶段：M4~M6 只做图片显示，音轨要到 M7 才接进来。
不加这个参数时，工具要求每个场景的图片和音轨都齐备，缺一个就拒绝动卡。

**本机 TF 卡固定是 `G:`**，所以盘符不用写：不写就用 `G:`，工具还会打印卡的容量
（例如"共 15.9 GB"）供你对照是不是这张卡。要写别的卡/读卡器时才显式给出盘符，
这时会打印一行警告提醒你别写错设备。双击运行（没有任何参数）只会打印用法并等你
按回车，不会碰卡。

**盘符安全闸**：这个工具会把整只卷清空（根目录全删 + 覆写可用空间），所以它只肯
写两条件都满足的卷——是本机固定盘符 `G:` **且** 容量不超过 64 GB。任何一条不满足
（比如手滑敲成 `E:`，那是一块 300 GB 的数据盘）都会直接拒绝，**连 `--yes` 也绕不
过去**，必须显式加 `--force-drive` 才放行。`--dry-run` 只打印警告、不拦（方便先
看计划）。

工具按四步执行：

1. **破坏旧签名**：把卡上所有 `.bmp` / `.aud` 文件开头的 `BM` / `MMAU` 改成 `XX`，
   让残留扇区不会再被 FPGA 扫到
2. **清空可见文件**
3. **覆写可用空间**：写一个全 0 大文件占满可用空间再删除，强制文件系统重新分配，
   盖掉任何通过文件系统已经看不到的历史残留
4. **按场景顺序写入**：`场景0 图片 → 场景0 音轨 → 场景1 图片 → …`，写完全部
   回读签名校验

### 比官方样例的 sync_to_sd.py 强在哪

官方脚本只破坏"在文件系统里还看得见"的旧图片头。如果图片是**手动删除**的，或者用
别的工具删的，那些扇区里的旧 `BM` 依旧存在，FPGA 照样会扫到——官方 README 里
「直接在电脑上删除无效」说的就是这个坑，但脚本本身并没堵上。

本工具的第 3 步专门堵这个洞，而且不需要管理员权限（走文件系统而非裸设备）。

### 安全设计

* 素材先在**动卡之前**点清，缺图或缺音轨直接退出，不会出现"卡清了才发现素材不齐"
* 拒绝 C 盘根目录
* 非试运行模式要求手动输入 `yes` 确认（`--yes` 可跳过）

## 6. 已知偏差

**音频采样率实际为 48.028 kHz，不是精确的 48 kHz。**

音频主时钟由 50 MHz 输入经 PLL 整数分频得到 12.295082 MHz（目标 12.288 MHz），
偏差 0.057%。Eagle 系列 PLL 的 `REFCLK_DIV` / `FBCLK_DIV` / `CLKCx_DIV` 都是
1~128 的整数，推导后无法得到精确的 12.288 MHz。

影响：音乐播放速度偏快 0.057%（3 分钟的曲子提前约 0.1 秒结束），听感无法察觉。
官方样例用的是同一套 PLL 参数，其文档里把 12.295 直接写作"12.288"。

处理方式：ACR 包按**实际时钟**计算 CTS/N，让 HDMI 接收端按真实速率还原音频时钟。
