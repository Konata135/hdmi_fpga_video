## 1. 需求基线

功能对齐官方样例（TF 卡 BMP 播放 + HDMI 输出 + 按键 + 音频），但**代码全部自研**。
相对样例的三处改动：图片 4→8 张；8 张按样例的 32 位/像素要 9.375 MiB 超出片内 8 MiB SDRAM，
故改 **24 位紧凑存储**（8 张 7.03 MiB，87.9%）；自研 SDRAM 控制器取代样例的三个加密文件。
不解析文件系统，按扇区扫描 `BM`。

  纯色时也正确，说明不是采样漂移、不是温度劣化）。

**画面偏移已闭环**（2026-10-17：修法上板验证，**多次复位无偏移**）。现象曾是：图片能显示，但整幅图
水平/垂直偏移（并沿行回绕出第二份），每次复位偏移量与方向都不同。

**根因（2026-10-17 更正）**：**读通路与显示的帧边界没有对齐**。画面读通路是*连续*走画面的，
而"画面接管屏幕"发生在 `frame_first`（**显示**的帧边界）；接管那一瞬间读通路可能正处在
**某一行中间**（→ 水平偏移 + 行内回绕出第二份）或**任意一行**（→ 垂直偏移），
走到哪儿取决于复位的时序 ⇒ 每次都不一样。**这不是缓冲深度问题。**

**已试过并否掉的修法**：把字缓冲从 256 字加深到 512 字（一行 480 字）+ 整行门限。
分布式 RAM 加深后 hold 余量从 +30 ps 掉到 **+14 ps**，实板上反而**完全不出图**（只有彩条），
已回退（提交 `6afe54d`）。将来若确实需要"整行在手"，必须先把这块 FIFO 改成 **BRAM**
（读是同步的，读通路要改成提前一拍预取）。

**修法（2026-10-17 已实现）**：让读通路的行走**与显示的帧对齐**再接管。三处：

* `mm_frame_rd` 多了 **`restart`**（翻转输入，与 base 变化走同一套 re-arm）和
  **`pix_frame_next`**（显示帧边界前一个消隐像素）。re-arm 之后像素侧**阻塞到帧边界**才开始
  交付（`align_wait`）；缓冲在这一帧里照常灌满（`can_topup` 不看 `align_wait`），所以第一行是完整的。
* **一次显示帧的消耗 = 整张图**（640×480 像素 = 230400 字），所以只要**起点**落在帧边界上，
  之后每一帧都自动对齐。
* `top.v`：`frame_display` 上升沿发一次 `restart`，把 `frame_show` 的决策从 `frame_first`
  改成 **`frame_next`**（在边界前一个消隐像素上决策并寄存，帧的第一个像素已经是画面的）。
  `pix_ready` 改成**锁存**的"自上次 restart 以来灌满过"：瞬时半满门限正好压在补充周期的低点上，
  帧边界采样会读到"未灌满"，画面会整帧掉回彩条。
  **这条 `restart` 就是 M6 切图的挂钩**：换 base + 发一次 restart，新画面会落在对齐帧上，
  不需要别的手段。
* 测试台：`tb_frame_rd` / `tb_frame_chain` 的检查从"交给我的像素序列对不对"升级为
  **"屏幕第 n 个位置显示的是不是画面第 n 个像素"**（原来那种检查看不见偏移），并各自模仿
  top 的接管规则（`restart` + `frame_next` + `pix_ready`）；`tb_frame_rd` 还覆盖了
  "载入落在帧中间"和"帧中间 restart"两种情形。

**板上已验证**：多次复位画面无偏移。若以后再出现偏移，先看页 19 的状态机在不在 `1`（等突发数据）
附近来回，以及页 8 的读通路下溢——"帧边界没等到"和"对齐算错了"是两件不同的事。

**M6（已实现，待上板）**：8 张图轮播。**交互按用户要求：一个开关控制自动轮播、一个按键切下一张。**

* `mm_pic_sched`（新）：按槽位顺序装载，槽位 0 先装好就上屏，其余在后台继续（读走突发口、
  写走单字口）；KEY2 = 下一张（在**已装好**的图之间走，含回绕）；SW1 = 自动轮播开关（1 秒一张）。
  **周期由 SW2/SW3 选**（C7/C6，2 位：0.5/1/2/4 s，改档时从新档重新计时），显示在页 15。
  某个槽位反复装不上：等 1 秒重试，最多 3 次，然后放弃该槽位继续装后面的——**一张坏图只损失一张**。
* `mm_key_debounce`（新）：按键/开关消抖（10 ms），按键给"按下"脉冲（只在 0→1 给一次），
  开关给干净电平。板上按键按下为低，开关拨上为 1（见 `doc/参考-官方` 手册 15/16 节）。
* `mm_img_load` 的 `FRAME_BASE` 参数改成 **`frame_base` 输入**（槽位运行期可变），
  top 用移位加法算 `base_i = (i × 225) << 10`，不用乘法器。
* 切图落到对齐帧上：帧存槽位号 + `disp_tgl` 翻转握手跨到存储域（值先稳定、再发边沿，
  不并行同步多比特），**在垂直消隐窗口里**改 base + 发 `restart`——停走路的代价藏在消隐里，
  屏幕上不会出现冻结的一帧；之后 M5 的 restart 机制保证新画面从帧边界的第一像素开始。
* 数码管**页 15** 改成轮播页：当前图号 / 已装张数 / 自动开关状态。
* **M6 上板结论（2026-10-17 复测：一切正常）**：现场那两个症状（切图偶尔退回彩条、某些图整屏纯色）
  的成因是"存储侧在等一个永远不会来的冲洗确认"——**请求被丢掉且不会重发**。定位靠页 16 的失败快照
  （`A01` = `mstate = M_FLUSH` + 缓冲空 + 无突发在飞），修法是下面 (c)(d)(e) 三条。
* **救援线（2026-10-17 加，保留为常驻安全网）**：板上开轮播后按 KEY2 偶尔退回彩条，仿真复现不出来。于是：
  (a) 读通路连续 **4 帧**没灌满就**单独复位读通路**（`rd_reset`，不动 SDRAM 控制器、不动帧存与图，
  重启后行走的还是当前槽位，画面自己回来）；(b) 失败瞬间的 `{mstate, app_ok, br_busy}` 与字缓冲用量
  锁存到**页 16**，`d2` 是救援次数。**下次再出先读页 16 的 d4**：`2` = 冲到一半卡住（握手），
  `1` + `br_busy` = 突发没收完，`0` + `app_ok` = 取数根本没启动。
  **板上第一次读数（页 15 = `180`、页 16 = `A01`）**：`d4 = A` 就是 `mstate = 2 (M_FLUSH)`、
  缓冲几乎空（`d3 = 0`）、没有突发在飞 ⇒ **存储侧在等一个永远没来的"冲干净"确认**，与"握手请求被丢"
  完全一致。据此后来又补了三处：
  (c) `mm_frame_rd` 的 arm **在 `M_FLUSH` 中不再重复翻转 `resync`**（见那条注释）——**这条护栏当时
     只有注释、没有代码**（补丁丢了），所以现场那颗 bit 里它其实是开着的，正好是"两个 resync 翻转
     在像素侧同步器里互相抵消"那条路径；
  (d) `M_FLUSH` 里那个确认**两毫秒不来就重发请求**（本项目第 2 条教训：被丢掉的一拍请求 = 对面永久
     卡死，要重发到被接受为止）；测试台用"把像素侧按在复位里"造出无人应答，确认会重发（`tb_frame_rd`）；
  (e) 救援线的触发从"没灌满"放宽到 **"没灌满 或 字缓冲空"**：前者=彩条，后者=像素侧在饿着（一直
     重复最后一个像素 ⇒ **整屏纯色**），两种都被同一个重启收拾。
* **调度器的失败判定（同期修）**：`load_phase` 是**粘住**的——失败后要到下一次尝试跑起来才被改写，
  只看它会把每次重试的第一拍就判成失败：重试被瞬间烧光、槽位被跳过、装载序列错位。判据改成
  **`load_phase == F && !load_busy`**（"它说失败"且"它已经停了"），并给"等 busy"加了超时重发。
  `tb_pic_sched` 的假加载器改成和真的一样**不提前清标志**、并让槽位 1 **只失败一次**（重试必须真的
  装成）、槽位 2 一直失败（必须被放弃）——旧判定下这个测试台会报 4 条错，确认它有证伪能力。
  已排除的：并发装载（`tb_frame_chain` 新增"槽位 0 在屏上时装槽位 1"的测试，12 帧不受影响）、
  双 arm（base 变化与 restart 其实落在同一拍，只 arm 一次；`mm_frame_rd` 仍加了"冲刷中不重复触发"
  的护栏，注释见那里）、时钟相位（把测试台像素时钟挪半个相位重跑仍全绿）。
* 坏图/非标分辨率不需要额外机制：扫描阶段只把 640×480/24 位/未压缩、长度自洽的 BMP 记进表，
  其余根本不进表；加载失败由调度器重试（见上）。
* 仿真：`tb_pic_sched`（装载顺序、单次一个、按键/开关走位与回绕、坏槽位跳过）、
  `tb_key_debounce`（抖动、一次按下、长按不重复、低有效）。

**上板要看的**：页 15 的 `d4` 按 KEY2 逐张跳、按开关后自己跳；`d3` 最终等于卡上图数（≤8）；
切图瞬间不应出现冻结的一帧。

## 4. 经验教训（一条一行，全部真栽过）

1. **时序为负不是背景信息，它就是故障本身。** "SDRAM 器件从不驱动数据总线"查了三天，
   最后是修掉一条"工具永远无法收敛"的路径后器件立刻应答——先让 `SWNS/HWNS` 清零，再看现象。
2. **共享端口/总线：被丢掉的一拍请求 = 对面永久卡死。** 请求只在 `ready` 拍被采样，
   而 `ready` 会被 refresh 或别的端口抢走；一拍宽的请求丢了以后，状态机等一个永不到来的完成。
   正解是**重发到被接受为止**（写侧加载器本来就这么写，所以它从没卡过；读侧照做后画面立刻出来）。
3. **能读错的仪表比没有仪表更坏。** 页 15/16 那两门采样仪表读数不属于任何真实来源
   （"文件里根本没有那种颜色"戳穿了它），已删除。**新仪表在用它下结论之前必须先能证明它读的是什么。**
4. **写完模块要顺手接上所有实例化点。** `mem_clk_sft`（采样时钟）和 `pix_ready`（"缓冲已灌满"）
   都在端口表里躺了很久却没接线，各自对应一次事故。加端口后 grep 一遍所有实例化。
5. **位宽截断是老朋友**：`3'd8`（状态机把完成当等待）、`4'd16`（数码管永远停在页 0）。
   宽一点的常量写成 `5'dN`，状态/寄存器先算好需要几位。
6. **看日志要看整份**：截断警告在日志前段；命令行流程写的是 `td_<时间戳>.log`，`run.log` 是 GUI 的。
7. **跨域搬多比特量不能靠并行同步器**：值只变一次时，各位可能锁到不同时刻并永久保留
   （曾出现"字节掩码说四个字节全对、值却说不对"的自相矛盾读数）。要么握手，要么等源稳定后**整字拷贝**。
8. **定时序类问题先让工具报告仲裁，别先改逻辑猜**：时钟相位/角色/BUFG 一共烧了四次板，
   答案第一时间就在时序报告里；官方 sdc 对同一接口早就写了 `set_false_path`。
9. **单点采样会误判**：采样时刻与想抓的像素对不齐就得出"不属于任何来源"的值；
   而现在页 17/18/19 用的"实时窗口 + 活计数器"才是可靠形态（窗口重起、值本身就稳定）。
10. **"读到数据" ≠ "读到该读的数据"**：长度对不代表位置对（加载器按字节数计数不会露馅）；
    仪表要能回答"**是这份数据吗**"，而不只是"是空白吗"。页 9~12 就是为此加的。
11. **仪器盲区要主动找**：`0xFF` 计数只能否掉"全白屏"，否不掉"整屏被拍平成别的纯色"；
    这个盲区让"纯色"多查了好几轮。每加一门仪表都问一句"它读不出来的是什么情况"。
12. **文档/工程文件的两处纪律**（README 第 6 节展开）：改 `.al` 要 TD 关着、
    命令行流程要改 `syn_1`/`phy_1` 两份 `.prj`；`.gitignore` 排除构建产物、
    厂商样例 `官方示例/`（含对方加密 IP）不入库。
13. **检查要能证伪那个故障。** `tb_frame_rd` 原来把读通路交出的像素**按顺序**逐个比对，
    **偏移它根本看不见**——一幅整体平移的图交出的序列一模一样。所以画面在板上偏了一个星期，
    仿真一直全绿。改成按**显示位置**比对（屏幕第 n 个位置必须是画面第 n 个像素）之后，
    偏移立刻被测出来。加检查时先问："如果我怀疑的那个故障真的发生了，它会不会一样通过？"
14. **测试台漏接输入端口 = 悬空 z，模块拿它当条件就会得到 x。** `tb_sdram_selftest` 没接探针的
    `pic_go`，而探针用 `pic_go ? S_FIN : S_BWG` 选下一状态 ⇒ 状态机进 x、`done` 永不来，
    该测试台一直在 FAIL（综合/上板没事，因为 top 里这个端口是接上的）。例化模块时按端口表
    逐个对一遍，别只补自己新加的那几个。
15. **模块之间的"通告"是契约，测试台要测契约的那一半。** `mm_pic_sched` 答应 top：第一张图装好后
    翻转一个握手位，top 才敢让读通路取数。我把这一句写成了条件式（只在"屏幕上那个槽位还没装好"时
    才翻转）——正常情况槽位 0 先装好、本来就选中它，于是**一次都不通告**，板上只出彩条（图都装进去了，
    没人告诉读通路去哪儿读）。`tb_pic_sched` 当时只数了"按一次键会不会翻转一次"，没数"第一次通告有没有
    发生"，所以它全绿。补的检查我拿旧写法跑过一遍，确认它会 FAIL（检查要能证伪那个故障）。
16. **多驱动（同一个 reg 在两个 always 块里赋值）只有综合会抓。** ModelSim 的 `vlog` 连 `-lint`
    都不报（0 警告，仿真还能跑），TD 综合直接报 `net 'x' is constantly driven from multiple places`
    并把它变成 black box。这类错别指望本地语法检查，**改完 RTL 一定跑一遍 TD 综合**再看行为。
17. **现场故障复现不出来时，别赌一个"大概是它"的修法：先让它可观测、会自愈，再去读仪表。**
    M6 的"开轮播后切图掉回彩条"（2026-10-17）在仿真里怎么造都不出（并发装载、切图序列、时钟相位
    全试过），我就把读通路的失败快照锁存到页 16、并给它一条"4 帧没灌满就单独重启读通路"的救援线——
    下次现场出问题，读一次 `d4` 就能把"握手卡住 / 突发没收完 / 取数没启动"三类原因分开，
    而不是继续猜。**同时要承认：救援线只是让演示不退化成彩条，根因还得靠那次读数。**
18. **补丁要核对"代码真的落地了"，别只看注释。** 上面那条"冲刷中不再重复翻转 resync"的护栏，
    我的补丁把注释写进去了、代码没写进去（提交 `d654e96` 里只有注释）。于是现场那颗 bit 一直带着
    那个隐患跑，我却在汇报里说它已经有了——**代价是用户多烧一次板**。改完逐条 `git diff` 对照，
    别信"我记得加过"。
19. **粘住的失败标志要连"忙/闲"一起判。** `mm_img_load` 的 `phase` 在失败后保持 `F` 直到下一次
    尝试跑起来；调度器只看 `phase == F` 就把每次重试的第一拍判成失败，重试被瞬间烧光、槽位被跳过。
    判"失败"要判**"它说失败"且"它已经停了"**（`F && !busy`）。测试台的模型要照真实的"不提前清标志"
    才测得出来——模型比实物"更干净"就等于没测。
20. **Verilog 的两个小坑（M7 音频源上踩的）**：`tri` 是保留字（网络类型），不能当变量名；
    `>>>` 只有在左操作数是**有符号**时才做算术右移——三角波下半周因此变成 4.19e6 的正数，
    是测试台的"峰值"和"过零"两个检查同时报错才逼出来的。测试台里比较有符号采样也要 `$signed()`，
    否则负数在无符号比较里全都"大于零"。

## 5. 当前工程参数（改东西时对照）

* 时钟：50 MHz 输入 → PLL：C0 = 25 MHz 像素 / C1 = 125 MHz 串化 / C2 = 62.5 MHz 180° 给 SDRAM 宏 /
  C3 = 62.5 MHz 存储域逻辑 / C4 = 62.5 MHz 180° 采集备份。
* 存储域 62.5 MHz 是**故意的**：SDRAM 数据在一个器件周期内都有效，采样点到跳变约有半个周期
  （8 ns）余量；带宽 62.5 M 字/s，而 640×480@60 只要约 13.8 M 字/s。
* 帧存布局：图片按 BMP 顺序自下而上写入，每行 480 字（1920 字节）；读通路**反向**走行
  （BMP 底在上），每行必须切在器件行边界（256 字）内。
* 自检探针地址在存储空间末尾（`0x1FFFFF` 与 `0x1FFE00`），任何帧都碰不到。
* 当前 route 后的时序：SWNS 约 **+0.80 ns**、HWNS **+0.02~0.07 ns**（两端 0 违例，逐次构建会浮动）。
  **最薄的一直是 `u_frame_rd/u_word_fifo` 那条写指针 → 分布式 RAM 的 hold 路径**（M6 那次落到
  +0.014 ns）。它就是 README 里说的"将来要改成 BRAM"的那块；真出随机错像素，先看这里。
