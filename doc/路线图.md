# 实施路线图

原则：**每一步都能单独验证**，不堆功能。前一步不稳就不进下一步。

**交付约定**：每次改动后，回复末尾必须给出"下一步上板操作 + 预期现象"，
并同步更新 `README.md` 第 4 节。这样即使换会话接手，也知道板子上该看到什么。

## 需求基线（2026-10-12 确认）

功能、TF 卡格式、图片读取方式全部对齐官方样例；代码全部自研，不使用厂商加密 HDL。

**主链路**（与赛题解读一致）：

```
TF 卡进 → SPI 读 → BMP 解析 → 片内 SDRAM 存帧 → HDMI 出画面和声音
```

这条链路立住了，框架就清楚；所有加分项都是往这条流水线上插模块。

**四项硬性交付要求**：

| 要求 | 关键指标 | 技术落点 | 对应里程碑 |
|---|---|---|---|
| ① 读图显示 | 640×480、24-bit RGB 非压缩 | SPI 读取 + 解析 + 帧缓存 + HDMI | M3~M6 |
| ② 切换轮播 | 画面连续稳定、无闪烁 | 按键消抖 + 帧切换时序对齐 | M6 |
| ③ 音频输出 | HDMI 输出 48 kHz 音频测试音 | I2S 音频通路 + HDMI 音视频复用 | M7 |
| ④ 稳定运行 | 上电即可运行 | QSPI Flash 固化 + 冷启动演练 | M13 |

**相对官方样例的改动**：

1. 图片数量 4 → 8 张
2. 帧存改为 **24 位紧凑存储**（3 字节/像素）。每像素 32 位的样例布局下 8 张需要
   9.375 MiB，超出片内 SDRAM 的 8 MiB；24 位紧凑存储 8 张占 7.031 MiB（87.9%）。
   每行 640×3 = 1920 B = 480 个 32 位字，整行对齐，打包相位每行归零。
3. **自研 SDRAM 控制器**。官方样例的初始化/刷新/读写时序是三个加密文件
   （`sdr_as_ram.enc.v` / `sdr_init_ref.enc.v` / `sdr_wrrd.enc.v`），按"不使用厂商加密
   HDL"的要求需自行实现；器件引脚接口原语 `EG_PHY_SDRAM_2M_32` 属于硬件事实，继续使用。
4. 8 张全部预加载后切图只改显示基地址，不需要样例的双缓冲乒乓，天然无撕裂。
5. **音频升级：每个场景自带一段音乐**。样例是片内 ROM 里的四段固定音调（C4/E4/G4/C5），
   按图号切换；我们改成每张图配一条独立音轨，音轨与图片一起写在 TF 卡上，切图时同步
   换曲。音轨格式见 `doc/TF卡文件格式.md`。

   演示模式定为**方案 A：固定间隔轮播**（2026-10-13 确认）：

   * 自动轮播间隔默认 **12 秒**，做成可调参数
   * 音轨按 **10~20 秒的可循环片段**准备，到点被切掉，不够长则循环
   * `key1` 手动切下一张，`key2` 开关自动轮播（与官方示例的按键行为一致）
6. **配套工具自研**：`tools/prepare_images.py`（图片转 BMP）、`tools/prepare_audio.py`
   （音乐转 48 kHz 立体声音轨）、`tools/write_card.py`（清卡并按顺序写入，M4 完成后提供），
   取代官方样例的 `convert_images_to_bmp.py` 与 `sync_to_sd.py`。

**音轨方案的资源账**：

| 项 | 数值 |
|---|---|
| 数据率 | 48 kHz × 2 声道 × 16 bit = 1.536 Mbit/s（192 KB/s） |
| SPI 占用 | 约 1 个扇区 / 2.7 ms，25 MHz 下不足 8%，余量充足 |
| SDRAM 音频环形缓冲 | 256 KB（约 1.33 秒），用于隔断读卡抖动 |
| SDRAM 总占用 | 8 张图 7,372,800 B + 缓冲 262,144 B = 7,634,944 B（91.0%），余 0.72 MiB |

完整的容量核算、帧缓存基地址与余量敏感性见 `doc/SDRAM内存映射.md`。

## M2 自研 HDMI 发送链路（已完成）

自研模块：`mm_tmds_encoder` / `mm_hdmi_serializer` / `mm_hdmi_tx`

取代了原先例化的安路加密 HDMI IP 核（`hdmi_1_4b_transmitter_core_wrapper`）与官方
PHY 包装（`hdmi_phy_warpper` / `lane_lvds_10_1`）。现在工程中不存在任何厂商 HDL 文件，
只使用器件原语。

* `mm_tmds_encoder`：TMDS 8b/10b 视频编码 + 4 个控制字符 + 逐通道游程不均匀度
* `mm_hdmi_serializer`：移位寄存器 + `EG_LOGIC_ODDR` 的 10:1 串化，严格最低位先发
* `mm_hdmi_tx`：控制期 / guard band / preamble / 视频数据期的行结构，三路数据 + 时钟通道

协议要点见 `doc/HDMI协议笔记.md`。

为了在没有示波器的情况下定位故障，M2 加了 6 位数码管状态显示（`mm_seg_display`）。
它只用 50 MHz 晶振和上电复位，不依赖视频/存储通路，别的模块崩了它照样能报。

状态字布局（`rtl/top.v` 里组装，逐里程碑填充）：

| 位 | 含义 |
|---|---|
| d5 | 状态码：0=复位 1=上电等待 2=图像链路就绪 3=卡初始化 4=卡就绪 5=扫描中 6=加载中 7=播放中 E=错误 |
| d4 | 当前场景号 |
| d3 | 扫描到的合法图片数 |
| d2 | 错误码 |
| d1 | 心跳（0~F，4 Hz） |
| d0 | 保留 |

扫描参数：6 位、200 Hz、位选低电平有效、段码共阳（低电平点亮），
`seg_data[6:0] = {g,f,e,d,c,b,a}`、`seg_data[7]` 为小数点。
若上板后数位左右顺序是反的，只需在 `mm_seg_display.v` 里对调 6 条位选赋值。

## M3 TF 卡 SPI 物理层（自研协议栈）— 仿真完成，待上板

自研模块：`mm_spi_master` / `mm_sd_cmd` / `mm_sd_init` / `mm_sd_sec` / `mm_sd_probe`

* [x] `mm_spi_master`：自研 SPI 主机，模式 0，半周期由 `clk_div` 运行时给定
      （初始化 100 kHz / 数据 25 MHz 用同一套硬件），片选交给上层以保证命令序列连续
* [x] `mm_sd_cmd`：命令层 —— 48 位命令帧（含 CRC7）、响应轮询、R1/R3/R7 解析、
      片选帧定界、无响应超时
* [x] `mm_sd_init`：初始化序列 CMD0 → CMD8 → CMD55+ACMD41（轮询直到就绪）→ CMD58，
      含 v1 卡识别、OCR 读取与高低容量判定、ACMD41 重试上限
      （已接入顶层：上电后每秒尝试一次，数码管 d4 显示当前阶段）
* [x] `mm_sd_sec`：CMD17 单扇区读 —— R1 → 0xFE 数据令牌 → 512 字节 → CRC16
      （只收不校验）。整段读保持片选不释放，512 字节以
      `data_valid` / `data_index` / `data_byte` 流式输出；v1 卡按字节寻址时
      `byte_addressed` 把 LBA 左移 9 位。四类等待都有上限：不回 R1、不回令牌、
      数据错误令牌 `0x0X`，各自带错误码退出，绝不挂住
* [x] `mm_sd_probe`：把上面两块串成 M3 验收链 —— 初始化 → 读 LBA0 → 校验尾部
      签名 `55 AA` → 解析分区 1 的类型 / 起始 LBA / 扇区数，容量按
      `向上取整(扇区数 / 2^21)` 换算成 GiB，并把 d4/d3/d2 三个数位的内容
      准备好
* [x] 重试机制：读失败先重试 3 次（间隔 1 ms），仍失败就把卡重新初始化一遍，
      之后无限循环；上电后每 1 秒尝试一次，中途插卡也能接上
* 验收：读出 LBA0 的 MBR 尾部签名 `0x55AA`，连同容量信息显示在 LED 上。
      上板看 d4 停在 `A`（签名校验通过），d3 d2 显示十六进制 GiB 容量
      （8 GB 卡显示 `08`）；失败则 d4=`F`、d2 给错误码

### 自检结果

```
tb_spi_master  RESULT: PASS -- SPI master verified
tb_sd_cmd      RESULT: PASS -- SD command layer verified
tb_sd_init     RESULT: PASS -- SD initialisation verified
tb_sd_sec      RESULT: PASS -- SD sector read verified
tb_sd_probe    RESULT: PASS -- initialise, CMD17, MBR check and retries verified
```

`tb_spi_master` 逐项核对：SCLK 半周期恰为 `clk_div` 个时钟、每字节 8 个上升沿、
MOSI 高位先出且与从机收到的字节一致、从机发来的字节完整收到、`busy` 覆盖整个传输、
`done` 每字节恰好一次、慢分频（初始化速率）同样正确。

`tb_sd_cmd` 用规范给定的标准答案核对命令帧，这是命令层唯一可从外部独立验证的数字：

```
CMD0 -> 40 00 00 00 00 95
CMD8 -> 48 00 00 01 AA 87
```

另外核对：R1 捕获、R3/R7 的 4 个附加字节、卡延迟应答时的轮询计数、片选帧定界，
以及卡完全不响应时的超时路径。

`tb_sd_init` 用行为级卡模型核对：命令顺序（CMD0 → CMD8 → CMD55+ACMD41 两轮 → CMD58）、
ACMD41 的就绪轮询、OCR 捕获与 bit30 解码成 `high_capacity`（实测 OCR=`C0FF8000`、
HC=1、识别为 v2 卡），以及**一张永不就绪的卡会重试到上限后报错退出而不是死等**。

`tb_sd_sec` 同样用规范给定的标准答案核对命令帧：

```
CMD17, 参数 0        -> 51 00 00 00 00 55
CMD17, 参数 0x0A00   -> 51 00 00 0A 00 C9    （v1 卡按字节寻址：LBA 5 × 512）
```

测试台自己用**多项式除法**（把命令左移 7 位再除以 `x^7+x^3+1`）重算一遍 CRC7，
这是与 RTL 逐比特循环完全不同的写法，并且先拿 CMD0→`95`、CMD8→`87` 两个公开值
自检过再使用。数据阶段核对：512 个字节恰好各来一次、`data_index` 与字节序号逐拍
相符、CRC16 两字节被移进移出但没有混进数据、片选全程保持到结束才释放；四种失败
路径分别核对错误码 1/2/3/4 以及保留下来的 R1 和错误令牌；最后再核对"读一半时拉复位"
能立刻清掉 `busy` 并放开片选。

`tb_sd_probe` 用一张带 MBR 的行为级卡跑完 5 个场景：

1. 干净卡：签名通过，分区类型 `0C`、起始 LBA 2048、扇区数 `0x00E90000`
   （7.28 GiB，即"8 GB 卡"）→ 容量显示 `08`，只读一次
2. 第一次读中途掉数据 → 重试后第 2 次成功，没有重新初始化（实测这次以错误码 4
   "数据错误令牌"收场）
3. 第一次读回 R1 错误位 → 同上，第 2 次成功（错误码 2）
4. 连续三次签名不对 → 重新初始化一遍（CMD0 出现第 2 次）后第 4 次成功（错误码 5）
5. 一张永远不就绪的卡：反复重试、永不锁死，d4 停在 `F`、d2 = `7`

> 组合测试台验的是**重试与重新初始化策略**：每个场景都断言"第一次失败、之后成功"
> 以及失败确实被记了下来（场景 3、4 连错误码一起断言）。**具体某类失败对应哪个
> 错误码，由 `tb_sd_sec` 逐个锁死**——那里每次只造一种失败，四种失败路径各自的
> 错误码 1/2/3/4 都是硬断言。组合测试台的卡模型要同时伺候初始化、长数据块和多次
> 重试，它在一次长事务之后的字节定相只是近似，所以场景 2 里"掉数据"落到的错误码
> 由模型停在第几个字节决定，不断言具体值。

## M4 扇区级图片扫描 + BMP 头解析 — 仿真完成，待上板

**先纠正一处旧文本**：本节原来写的是"FAT32 解析（MBR → DBR → FAT → 根目录 →
簇链遍历）"，这与 2026-10-12 定下的需求基线冲突——基线写明"FPGA 不解析文件系统，
而是在卷内按文件头签名逐扇区扫描"，`tools/write_card.py` 和 `doc/TF卡文件格式.md`
都是按这条写的，官方样例的实际代码也是裸扇区扫描（它文档里"FAT32 读取"的说法在
调试记录里已查证有误）。所以 M4 按基线做，标题一并改过来。

自研模块：`mm_sd_scan`（扇区读复用 M3 的 `mm_sd_sec`，不新增 SPI 控制器）

* [x] `mm_sd_scan`：从 MBR 给出的分区起始 LBA 开始逐扇区扫；扇区首两字节命中 `BM`
      就校验 BMP 头（长度 / 像素数据偏移 54 / 640×480 / 24 位 / 非压缩），合法就写进
      图片表（最多 8 条，每条 = 起始 LBA + 文件长度）
* [x] 跳过式扫描：记下一张图后按头部声明的长度直接跳过去，不逐扇区爬完一张图；
      `MMAU` 音轨也按头部长度跳过（为 M7 预置，当前只用来跳，省掉几秒空走）
* [x] 三个终止条件，谁先到就停，保证一定会结束：连续 16 MB 没找到新图、总预算
      100 MB、图片表满 8 张
* [x] 扇区引擎仍然只有一个：`mm_sd_probe` 按阶段把同一个 `mm_sd_sec` 交给 MBR
      校验或扫描，不做引脚多路切换
* [x] 上板验证（2026-10-13）：上电后 d4 在 `b` 停约 5 秒（卡里 2 张图，扫完最后一张
      还要爬满 16 MB 空白区），随后稳定在 `C`；页 1 的 `709`、页 2 的 `A 0F` 都对。
      修复前的"完成后自己重跑"（3 位状态寄存器）已消失
* 验收：把扫到的图片张数与第一张图的起始扇区、长度显示出来。板上 d4 d3 d2 每 2 秒
      轮翻三页：页 0 = 阶段码 / 图片张数 / 错误码，页 1 = 首图占多少扇区
      （640×480 24 位 BMP = 921654 字节 = 1801 扇区 = `709`），页 2 = 容量。
      仿真里逐项核对起始 LBA 与长度，板上只报摘要

### M4 自检结果

```
tb_sd_scan     RESULT: PASS -- picture scan verified
```

`tb_sd_scan` 用一个"按需生成"的假卷核对扫描策略本身（不走 SPI，快而且能精确断言
读了几次）：

1. 空卷：按 gap 规则结束，恰好读 41 个扇区（gap 40 + 1）
2. 两张图 + 中间一条音轨：读 44 个扇区却记了 9403 个扇区的账，两条记录分别是

3. 六种坏头全部拒绝（magic 不是 `BM` / 宽度 320 / 位深 8 / 压缩 / 像素偏移 40 /

4. 表满：8 张全记录，第 9 张所在扇区**一次都没读**

永远不就绪的卡不锁死；**卡里没有图片文件时报错误码 6 并继续重试**。

## M5 SDRAM 帧缓存 — 整条图像通路接通，仿真通过；待上板

自研模块：`mm_sdram`（控制器）、`mm_afifo`（跨时钟 FIFO）、`mm_frame_wr`（帧写通路）、
`mm_frame_rd`（帧读通路）、`mm_img_load`（图片加载器）——五项全部完成，16 台自检全绿，
`top.v` 已把显示源接到帧存。剩下的是**双缓冲**与**上板验证**

**板级事实**（全部从官方样例的**非加密**部分查证：`global_def.v`、`timing.sdc`、
`IP/sdram.v`）：

* SDRAM 在**封装内**：`EG_PHY_SDRAM_2M_32` 是直连内部硬核的宏，**没有板级引脚**
  （样例的 `pin.adc` 里也确实一条 SDRAM 约束都没有），所以不用画引脚、不用算板上
  走线时序。
* 用法固定：`cs_n` 恒 0、`cke` 恒 1，命令编码在 {ras_n, cas_n, we_n} 上；**器件时钟
  用 125 MHz 180° 相移那一路**，控制器逻辑用 0° 那一路（样例 sdc 里明确列了
  "SDRAM controller internal 0-degree / 180-degree clock paths"）。
* 几何：4 bank × 2048 行 × 256 列 × 32 位 = 2M 字；应用地址 =
  `{bank[1:0], row[10:0], col[7:0]}`（21 位，与样例 `ADDR_WIDTH` 一致）。
* 刷新：64 ms / 2048 行 = 3906 个 125 MHz 周期一次，算法与样例 `global_def.v` 相同。

* [x] `mm_clk_gen` 增加第三路 PLL 输出 `mem_clk_sft`（CLKC2_DIV=8 / CPHASE=3，
      照抄样例的 125 MHz 180° 配置）
* [x] `mm_sdram`：上电静默 200 µs → 全 bank 预充电 → 两次自动刷新 → 写模式寄存器
      （突发长度 1、CAS 延迟 3）→ 就绪；之后按节拍自动刷新
* [x] **行命中访问**（M5 的带宽前提）：算一下就知道必须做——640×480 每行 1920 B、
      行时 32 µs，需要约 60 MB/s；而"每个字都激活一行 + 自动预充电"只有约 45 MB/s。
      现在同一行内的连续访问直接发 READ/WRITE（约 5 拍/字，约 100 MB/s），换行才
      预充电 + 激活，并把 tRAS/tWR/tRP 都做成显式守卫；读延迟从**命令发出时刻**计数
      （不依赖 FSM 进捕获状态的时刻，免得再被"进状态晚一拍"咬一次）
* [x] **突发读端口**（第二块带宽前提）：逐字请求一来一回要约 7 拍（≈15 M 字/s），
      而 640×480@60 需要 18.4 M 像素/s（每像素 3 字节）——都不够。新增
      `br_req/br_addr/br_len → br_dv/br_data` 突发端口：同一行内**每拍发一个 READ、
      每拍出一个字**（≈500 MB/s）。`tb_sdram` 用 120 字的突发核对数据，并断言
      "≤136 拍"（逐字往返会要 840 拍）——**定量证明是背靠背而不是逐个往返**
* [x] 应用侧一次一个 32 位字：`ready` 握手，字节掩码 `wr_dm`（1 = 该字节不写）
* [x] `sim/mm_sdram_device.v`：行为级器件模型，同时把协议规则当断言查（tRP /
      tRCD / tRFC / tMRD / tRAS、先激活后访问、CKE 与 CS 恒定），违规会打印并计数
* [x] `mm_afifo`：灰色码指针 + 两级同步器 + 两侧各一个 used 计数（帧写/帧读都要它）
* [x] 帧写通路 `mm_frame_wr`：SPI 字节流 → 每 4 字节打包成 1 个 32 位字（**小端**：
      每组的第一个字节落在 `[7:0]`）→ 经 `mm_afifo` 跨到 125 MHz → 按 `base_word+i`
      逐个写入。中途放弃的帧会被冲刷掉，新帧不会继承残留
* [x] 帧读通路 `mm_frame_rd`：**每拍一个像素**（突发读 + 字节移位器），`tb_frame_rd`
      全绿。迁移后曾红 20 项，用一轮探针（`tmp_dbg/tb_fr_probe.v` 把突发地址、送进
      缓冲的每个字、送出的每个像素一起打出来）分成三刀切开，三处都是真缺陷：
  * **突发长度没有受缓冲余量约束**：`burst_len` 写成 `row_left < cap_len ? row_left :
    min(room, cap_len)`，`row_left` 那一支把余量检查短路掉了，于是余量只剩 3 个字时
    照样要 12 个字。写满的缓冲会**静默丢弃**多出来的字，丢一个字就使 3 字节的像素
    相位错开一位 → 一帧后半段整体错位。改成真正的三者取小
    `min(row_left, room, cap_len)`
  * **换图从不冲刷**：`flush_pop` 生成在存储器侧，而 FIFO 的读指针在像素域，所以
    一个字节都没弹出，M_FLUSH 等 `fifo_empty` 永远等不到 → "换图后不再取数"。
    改成**读侧冲刷 + 握手**：存储器侧停手、翻 `resync`、等 `flush_done`；像素侧收到
    后把旧字节一个个弹掉，清空后回翻 `flush_done`，存储器侧才走新图。这样既不丢新图
    的头几个字，也不受跨域同步延迟影响
  * **把缓冲喂到满**：`wfull` 由**同步过来的**读指针算出，所以它比真实占用早几拍
    报满；旧逻辑只在 `room > 2` 时就发请求，把缓冲顶到 32/32，正好让这个滞后变成
    丢字（探针实测 `wused=32 rused=24`，即写侧眼里的读指针落后 8 个字）。改成
    **只补到四分之三**（`TOPUP` 参数，默认 `FIFO_DEPTH*3/4`），留四分之一余量，
    满标志的滞后再也咬不到
* [x] 图片加载器 `mm_img_load`：借 `mm_sd_probe` 里**同一个**扇区引擎（不新开 SPI
      控制器，也不做引脚多路切换），逐扇区把第一张图读进来，跳过 54 字节 BMP 头，
      边读边把像素字节推给 `mm_frame_wr`。不翻转——BMP 自下而上、帧存按文件顺序放、
      读通路倒着走行，三件事合起来正好正立。扇区读失败重试 3 次，失败上报且允许重启
* [x] 显示源从测试图案切到帧存：上电先出测试图案，扫描停在 `C` 且找到图时自动开始加载，
      加载完成后**在下一个帧边界**切到图片（帧中换源会出接缝）；没卡就一直保持测试图案，
      加载失败每秒重试一次
* [x] `mm_sd_probe` 增加**第二个扇区引擎客户端**（`aux_*`）：把引擎自身的握手与字节流
      引到模块外，加载器直接用。同一个时刻只有一个客户端有请求，所以引擎是"借出"而不是"抢占"
* [x] **时序收敛**：TD 综合 + 布局布线跑通，`SWNS +0.102 ns`、`HWNS +0.014 ns`、
      setup/hold 失败端点都是 0
      （hold 也正 `+0.014 ns`）。第一次跑出来是 **-3.918 ns / 75 个失败端点**，两轮修下来
      才干净——三处都是真问题，见调试记录：突发长度的组合链太长、跨域标志没同步器、
      32 位长度比较串在起始脉冲后面
* [x] 片内 SDRAM 自检 `mm_sdram_selftest`：上电后往存储空间末尾（`21'h1F_FFFF`，任何
      帧都用不到）写一个已知字 `A5A5_5A5A` 再读回比对，结果放在数码管**第 4 页**。
      做它的理由：控制器**不校验器件**——器件没被正确驱动时它照样按自己的时序发命令、
      照样回握手，于是"加载完成、画面切换"全是假的，读回来的是悬空总线的全 1（白屏）。
      有这一页，白屏就能一句话定性：`A A5` 是好的，`F FF` 是总线读回全 1，`F 00` 是写没落地
* [x] 自检**扩到两条读通路**（第 5 页）：四个"走位半字节"的字（`A5A50001` / `A5A50010` /
      `A5A50100` / `A5A51000`）先逐个单字写入，再用**突发端口**整段读回比对。
      必须分开测是因为**屏幕上真正走的是突发端口**，而两条路径的采样节拍不一样
      （见调试记录里"突发读整体差一拍"那条）；单字过、突发读回全 `FF`，就锁定读通路
* [x] **读采样点自校准**：`mm_sdram` 的读采样点做成可选（`rd_phase`：默认 / 提前半个
      周期（用 180° 时钟那一路采的副本）/ 再各加一个整周期），上电探针把四个点各试一遍，
      **选第一个能整字读回的点交给控制器**，之后图像通路用的就是标定过的点。
      整周期那个偏移**只对单字有效**（突发里移动整周期等于"取到下一个字"），所以标定
      特意优先选不需要整周期偏移的点（相位编号 0/1 排在 2/3 前面）。诊断结果显示在
      第 4/5 页：采样点掩码 + 字节匹配掩码，一眼能看出"是采样点问题"还是"器件不应答"
* [x] **加载器自检（第 6/7 页）**：这次上板两次都是"读到数据但整字不完全对"，而"白屏"
      要求**每一字节都是 `0xFF`**——一小撮错位比特不可能把整屏刷成纯白，所以白屏一定是
      另一个**系统性**原因。据此加了三条能看到真相的读数：
  * 页 6 显示第一张图的**起始扇区**（页 1 的 `709` 只是长度，位置错照样读满 921600 字节）
  * 页 7 显示加载器错误码 + 交出的**前 255 个像素字节里 `0xFF` 的个数**（照片是个位数，
    空白区是 `FF`）
  * 加载器读第一个扇区时**校验开头两字节是 `BM`**（扫描就是靠这两个字节认定文件的），
    不是就报错误码 4、一个字节也不交给帧写通路 —— 把"读到别处"从静默失败变成显式错误
* [x] 顺带把"帧写通路何时开工"挪到**头部判定之后**：原来先让写通路开工再发现头不对，
      会在失败路径上白起一帧；现在第一扇区的第 3 个字节（判定已落定）才发 `frame_start`，
      而像素数据从第 54 字节才开始，所以一个字节都不会漏
* [x] **把器件时序门限寄存化**（时序修复）：`wait_cnt`/`ras_cnt`/`wr_cnt`/`pre_cnt` 的
      "等到 tRP / tRCD / tRAS / tWR / tRFC / tMRD"比较各自存成标志位（`rdy_*`），FSM 只读
      标志位。原因：这些比较原本处在一条约 6 级锥的**头部**，那条锥一路通到 SDRAM 命令
      寄存器的使能端（7.8 ns / 8 ns，其中 5.08 ns 是走线、末跳扇出 11）。门限只会晚一拍
      成立 = 对器件下限更保守；而且读捕获计数**绑在命令时刻**上（单字路径在
      `issue_access` 装载 `lat_cnt`，突发路径的 `br_wait` 保持到第一个 READ 才计数），
      命令整体后移时捕获跟着后移，采样窗口关系不变
* [x] **请求判定寄存化 + 打包 FIFO 减深**（时序修复第二刀）：重跑后仍差 `-0.091 ns`，
      但绑的已是**另外两条**路径，说明第一刀生效了。**①** `mm_sdram` 新增 `S_DEC` 状态：
      请求到达那一拍只做锁存，行命中 / tRP 判定落进寄存器，下一拍再决定走哪条路——把
      "请求地址（来自 `mm_frame_rd` 自己的状态机，跨模块）+ 每 bank 已开行 + 门限"从
      状态寄存器的输入路径上摘下来（那条 8 级 / 7.8 ns）。代价是每次**新访问**多一拍，
      突发不受影响（所有 READ 都是进了 `S_BR_RUN` 之后连发的）。**②** 打包 FIFO 从模块
      默认的 1024 字缩到 128 字：字节侧 80 ns 才来一个字、字侧排空快得多，覆盖 SDRAM
      自身延迟只要几个字，而那条读多路选择器是 5.2 ns 走线（扇出 64、占该路径 68%）
      直接进 `wr_data`
* [x] **存储域降到 62.5 MHz**（第三刀，也是这一轮真正针对病因的一刀）：上板读回的
      原始值一直"大部分字节对、个别比特错，而且每次不一样"——这是**裕量不足**的签名，
      不是逻辑错。SDRAM 数据在一个器件时钟周期内有效，所以采样点到最近跳变的裕量约为
      半个周期：125 MHz 只有 4 ns，62.5 MHz 是 8 ns。带宽代价为零（突发端口每拍一个字，
      62.5 MHz = 62.5 M 字/s，而 640×480@60 只要约 13.8 M 字/s），而且 HDMI 串化器仍用
      另一路 125 MHz，**视频通路完全没动**。同时把"扫四个采样点自校准"那套**撤掉**：
      它把 32 个触发器挂在驱动 SDRAM 宏的 180° 时钟上，板子上反而更糟
* [x] **自检改成输出原始值**：页 4/5/6 显示帧存读回的**原始 32 位字**（12+12+8 位），
      页 7 是突发端口 + 字节匹配掩码，页 8 是"打包 FIFO 溢出 / 读通路像素下溢"两项体检。
      理由：只有"通过/不通过"的读数，一次上板只能否掉一个假设；原始值一次能否掉好几个
      （`A5A55A5A` 对 / `5A5AA5A5` 字节序反 / `00000000` 没写进 / `FFFFFFFF` 总线悬空 /
      每次不同 = 裕量不够）。所有诊断量都**只在探针结束时写一次**，避免跨域同步把两次
      结果拼成一个（上一版 `F08` 里 d3 与 d2 自相矛盾就是这个毛病）
* [x] SDC 补上**跨时钟域声明**（`con/hdmi_player.sdc`）：50 MHz 域与两路 PLL 时钟之间
      全部是异步的（每个跨越都走两级同步器 / 灰码 FIFO / 翻转脉冲），所以互设
      `set_false_path`；**但 `clkc[0]`（25 MHz）与 `clkc[1]`（125 MHz）之间刻意不设**——
      串化器的 /5 计数器依赖两者固定相位关系，那一段必须继续被检查
* [ ] 双缓冲：写一帧的同时显示另一帧
* [ ] 上板验证
* 验收：静态图完整显示，无撕裂、无错位

`tb_sdram_selftest` 特意不只比对"探针自己收到的值"：它另外直接查**器件模型阵列**里
那个地址的内容，否则探针即使什么都没写进去也可能自说自话地"通过"。

注意上面 `sample points = 1001`：在**仿真模型**里相位 0 和相位 3 都能整字读回（模型
的 tAC 是 0，数据正好在 180° 边沿翻转），而真器件有 5~7 ns 的 tAC，能用的点很可能不是
0——这正是这个自校准存在的意义：**板子自己挑**，而不是照模型的假设去猜。

`tb_frame_chain` 是 M5 的"整条链"证明：假卡 → `mm_img_load` → `mm_frame_wr` →
`mm_sdram` → `mm_frame_rd` → RGB，**逐点核对全部 3072 个像素**。假卡的字节流让每个
像素自带行号列号（B=行、G=列、R=标记），所以一次比较同时锁死"行翻转、列序、B,G,R→R,G,B、
以及整条写通路的打包与地址"。它比 `tb_frame_rd` 多出来的价值在**尺寸**：48×48 的图
每行 48 个字、共 2304 个字，必然跨过 SDRAM 的 256 字器件行边界，而 12 字宽的测试图
一次都跨不到——第一个真缺陷就是它抓出来的（见调试记录）。

`tb_frame_wr` 不是只看"写完了没有"：它直接读**器件模型里的存储阵列**，把每个字和
输入的字节流逐字比对（这样打包顺序和地址序列都无处可藏），再检查第二帧不动第一帧、
以及中途放弃的帧不会污染下一帧。最后一行的"SDRAM violation"来自器件模型的协议断言。

`tb_frame_rd` 把一个 4 行 × 16 像素的小图按 BMP 顺序填进器件模型（每个字节都编码了
它代表什么：B 存行号、G 存列号、R 是标记），然后扮演视频时序把像素收回来逐点核对——
一次比较同时锁死"行翻转（BMP 自下而上）、列序、B,G,R→R,G,B"三件事。另外验了换图时
旧字节确实被冲刷（诊断计数器 `dbg_flush_words`，由**像素侧**统计，因为冲刷是它在做）、
"不是当前显示源时不取数"、以及器件模型的协议断言为零。
