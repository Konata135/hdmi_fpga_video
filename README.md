## 1. 本工程的定位

这是一次**从零重写的原创实现**，不是官方样例的修改版，也没有引用任何厂商 HDL 源码。

| 类别 | 内容 | 说明 |
|---|---|---|
| 使用（器件/板卡事实） | 板上引脚定义、器件原语 `EG_PHY_PLL` / `EG_LOGIC_BUFG` / `EG_LOGIC_ODDR` | 相当于"用这颗芯片、这块板子"的既成条件 |
| 自研（本队原创） | 时钟与复位子系统、视频时序发生器、测试图案、**TMDS 8b/10b 编码器**、**并串转换器**、**HDMI 行结构（控制期 / guard band / preamble / 视频数据期）**、TF 卡 SPI 协议栈、扇区级图片扫描、BMP 解析、**SDRAM 控制器**、帧缓存调度、音频链路、交互控制 | 全部逐行自己写 |

官方样例（lab_ex4_tf / lab_ex5_i2s）与安路 SDK 中的加密 HDMI IP 核（`DVITransmitter` /
`TMDSEncoder` / `hdmi_1_4b_transmitter_core_wrapper`）**一处都没有进入本工程**：
HDMI 发送端从 TMDS 编码到四路串化全部自行实现。第三方代码占比为零。

## 3. 如何编译与下载

1. 用 Anlogic TD 6.2.1 打开 `prj/hdmi_player.al`
2. 顶层模块为 `top`
3. 依次执行 Synthesis → Physical Design → Download
4. HDMI 线接开发板的 **HDMI_B** 接口，另一端接显示器

### 上板状态指示：6 位数码管

板载 6 位数码管每秒刷新 200 轮，直接读状态字即可定位问题。它只挂在 50 MHz
晶振和上电复位上，**不依赖视频、存储任何一条通路**，所以别的模块崩了它照样能报。

```
 d5  d4  d3  d2  d1  d0
状态 场景 图数 错误 心跳 保留
```

| 位 | 含义 |
|---|---|
| d5 | 状态码：**2=像素域正在出帧 / E=像素域无帧**；后续 3=卡初始化 4=卡就绪 5=扫描中 6=加载中 7=播放中 |
| d4 | 当前场景号（M6 起）；此前的里程碑放的是 SD 阶段码 |
| d3 | 扫描到的合法图片数（M4 起）；读通后放容量高 4 位 |
| d2 | 错误码，0 表示无错误；读通后放容量低 4 位 |
| d1 | 主时钟心跳（50 MHz 域），0~F 以 4 Hz 循环——**不跳说明主时钟或复位有问题** |
| d0 | 帧计数（像素域），每 16 帧 +1——**它才证明视频时序在出帧** |

> 上表是各列的最终规划，**当前里程碑实际填入的内容见第 4 节**（那节跟着代码走）。

两者分属不同时钟域，正好用来切分故障：

| 现象 | 结论 |
|---|---|
| d1 不跳 | 50 MHz 主时钟或复位有问题 |
| d1 跳、d5=E、d0=0 | 像素时钟或视频时序没跑起来 |
| d1 跳、d5=2、d0 在跳 | 视频域正常出帧，问题在 HDMI 发送链路 |

> 如果 TD 拒绝打开手写的 `.al`，新建一个工程（器件选 `EG4S20BG256`，Family `EG4`），
> 把 `rtl/` 与 `con/` 下的文件按 `doc/路线图.md` 里的清单加入即可。

> **新增 RTL 文件后必须确认它在 TD 的文件列表里**。TD 会用自己的内存列表覆盖
> `prj/hdmi_player.al`，所以在 TD 已经打开着工程的时候手动改 `.al` 是无效的——
> 下次 TD 保存就把它冲掉了。表现是综合时报
> `xxx is a black box in ...`（模块定义没编译进去）。两种稳妥做法：**关掉工程
> 再重新打开**（TD 会重读 `.al`），或者直接在 TD 里右键源文件目录 → 添加文件。

> **综合日志里的 WARNING 要当回事**。TD 用 `HDL-5007` 这类警告报过真问题：比如
> "literal value 'd8 truncated to fit in 3 bits" —— 状态码 `3'd8` 被截断成 0，结果
> 状态机把"完成"和"等待"当成同一个状态，上板表现是"完成后自己重跑一遍"。只看
> ERROR 会漏掉它。
>
> **2026-10-16 又栽了一次同一类跟头**（`page <= 4'd16` 写进 4 位寄存器 → 截断成 0 →
> 数码管永远停在页 0 `C80`）。这次还暴露两条流程错误，都写进 `doc/路线图.md` 了，这里记要点：
> **①** 看日志要看**整份**、把 WARNING 全列出来——`HDL-5007` 这类截断警告出现在日志**前段**，
> 用 `Select-Object -Last N` 会把它滤掉；**②** 命令行跑流程时 TD 的日志是 **`td_<时间戳>.log`**，
> `run.log` 是 GUI 留下的，grep 错文件会把"别人构建的日志"当成自己的。

> **布局布线跑完要看 SWNS，不能只看"bitgen complete"**。时序没收敛也会生成 bit 文件，
> 上板表现是随机花屏或偶尔错像素——最难查的那一类。本工程目前是
> `SWNS +0.802 ns / TNS 0 / 失败端点 0`、`HWNS +0.046 ns`，余量很薄：**只要改了 `rtl/mem/` 或
> 跨时钟域的信号，就要在 TD 里重新看一遍 SWNS 是否仍为正**。
> 这 0.802 ns 的出处是"命令寄存器 → SDRAM 宏的引脚"那一组（48 个端点），它**要留在检查里**；
> 而**回程**（宏的 `dq` 引脚 → 采集触发器）必须照官方 sdc 那样声明成例外，否则工具会拿 SIP 模型里
> 一个 15.7 ns 的引脚延迟去要 8 ns 的预算，报 65 个**靠布线不可能收敛**的端点——2026-10-16 先被
> 这 65 个端点骗了一轮，当成"时序真退化了"。命令行也能跑（不用开 GUI）：
> 先 `prj/hdmi_player_Runs/syn_1` 后 `prj/hdmi_player_Runs/phy_1`，各自执行
> `E:\TD621\bin\td_commands_prompt.exe E:/TD621/scripts/DefaultFlow.tcl`（**脚本路径要用正斜杠**，
> 反斜杠会被 Tcl 吞掉、报成 `E:TD621scriptsDefaultFlow.tcl`），最后两行会打印 Setup/Hold 的 WNS。

## 4. 当前版本：上板操作与预期现象

> 这一节每次改动后都会更新，回答末尾也会重复一遍。烧写顺序固定：
> TD 打开 `.al` → Synthesis → Physical Design → Download → HDMI 线接 **HDMI_B**。

### 当前版本：M1 + M2 + M3 + M4（均已上板）+ M5 图像通路（待上板）

板上跑的是完整链路：**TF 卡 → 扫描找图 → 把第一张图读进帧存 → HDMI 出图**。
上电先显示内部测试图案（M1/M2 那条链的正常产物），一旦扫描完成（d4 走到 `C`）
且找到了图，就开始把第一张图读进 SDRAM；读完之后**画面在下一个帧边界切换成图片**。
没插卡或没有合法图片时它一直保持测试图案，并每秒重试一次，不会黑屏也不会卡死。

> 图片是 640×480 24 位非压缩 BMP，必须用 `tools/write_card.py` 顺序写进卡；
> 卡的准备见 `doc/TF卡文件格式.md` 第 5 节。

| 观察点 | 预期现象 |
|---|---|
| HDMI 显示器（插好图的卡） | 先出 8 条竖色条测试图案，约几秒后切换成 **TF 卡里的第一张图片**，画面稳定不动 |
| HDMI 显示器（没卡 / 卡里没图） | 一直显示测试图案（8 条竖色条 + 四边灰色细框 + 一个 64×64 方块斜向移动、约每 0.5 秒黑白翻转） |
| 数码管 d5 | **2** = 像素域正在出帧；若显示 **E** 则像素域没出帧 |
| 数码管 d4 d3 d2 | **每 2 秒轮翻四页**，见下面的页表 |
| 数码管 d1 | **跳得快**：主时钟心跳，0.25 秒一步，一轮 4 秒 |
| 数码管 d0 | **跳得慢**：帧计数，1 秒一步（每 60 帧），一轮 16 秒 |

> 两个位故意做成差 4 倍的速率，否则同时盯着看分不清哪个是哪个。
> 快的是 d1（50 MHz 主时钟域），慢的是 d0（像素域出帧）。
> 假如 d1 在跳而 d0 停住，说明主时钟正常但像素域没出帧。

### d4 d3 d2：十七页轮翻

三个数位放不下存储链路的全部信息，所以它们每 2 秒换一页。d5、d1、d0 的含义
始终不变。

| 页 | d4 | d3 | d2 |
|---|---|---|---|
| 页 0（阶段页） | 阶段码，见下表 | 已找到的图片张数 | 错误码，见下表 |
| 页 1（加载器读了多少） | 加载器**真读**了几个扇区（3 位十六进制，单位 512 字节；640×480 24 位 BMP 就是 `709`） | | |
| 页 2（容量页） | `A`（MBR 已校验） | 分区容量 GiB | |
| 页 3（加载页） | 加载阶段码，见下表 | 加载器错误码（见下表） | 交出的**前 255 个像素字节里有几个 `0xFF`** |
| 页 4 / 5 / 6（帧存读回） | **帧存读回的原始 32 位字**，每页 12 位（页 6 只放低 8 位），页 6 的 d2 是**能整字读回的那个采样偏移**（0/1/2） | | |
| 页 7（突发自检） | `A` = 突发端口的第一个字就是所问的第一个字 / `F` 不行 | 量出来的**错位字距**（0–3，`F` = 连写进去的图案都不是） | 能把突发对齐的**采样偏移** |
| 页 8（回环与体检） | `A` = **数据总线读回了控制器自己驱动的值** / `F` = 没有 | 打包 FIFO 的**溢出计数** | 读通路**像素下溢计数**（高字节，`FF` = 一直饿着） |
| 页 9 / 10（**画面首像素**） | 画面区**第 0 个字**（也就是文件里第一个像素的 B,G,R）里 R,G,B 的**高 4 位**：d4=R、d3=G、d2=B | | |
| 页 11 / 12（**画面顶行首像素**） | 画面区**第 229920 个字**（画面最上面一行的第一个像素，也就是屏幕第一行左边那个像素）的 R,G,B **高 4 位** | | |
| 页 13（**两段数据流在动吗**） | 读通路**收到的字**里"和上一个字不同"的个数（窗口 4096 个字，÷256：`FF` = 几乎每个字都不同 = 健康，`00` = 卡住） | 同上，低 4 位 | 读通路**送出的像素**里不同的个数 ÷256 的**高位**（`0` = 几乎不变；`1` ≈ 健康——文件自己算出来是 282；`3` = 几乎每像素都变） |
| 页 14（**加载的是哪张图**） | 加载器**被告知**去读的起始扇区（扫描表第一项的 LBA **÷16**，即 4 KiB 单位；一张图 = 112 = `70`） | | |
| 页 15（**送到 HDMI 的是什么**） | HDMI 发送器输入 `vout_rgb` 在**每帧第一个有效像素**处的粗色（R,G,B 各取高 4 位）：`888` = 测试图案的灰边框（画面没接管屏幕）、`000` = 画面自己的左上角（rgb 3,2,10） | | |
| 页 16（**同上，取中景**） | 同一信号在**每帧第 240 行第 320 列**处的粗色：画面在那里是 `98E`（rgb 152,138,230，人物头发附近），测试图案在那里是 `F0F`（品红条）或 `000`/`FFF`（移动方块路过） | | |

> 页 15 **单点会误判**：画面自己的左上角就是暗的，所以"画面在线上"和"线上恒为黑"都读 `000`。
> 页 16 那个点亮得多（`98E`，本设计别处不会出现），两页合起来三种情况一次分开：
> **图案**（`888` / `F0F`）= 画面根本没接管；**画面**（`000` / `98E`）= 画面确实送到了发送器、
> 问题在发送器内部或之后；**常量暗色**（`000` / `000`）= 发送器输入侧就被拍平了。

> 页 1 与页 14 是 2026-10-16 这一轮改的：页 1 原来放的是"扫描按 BMP 头算出来的长度"（一直是
> `709`，已经证过），现在改放**加载器真读的扇区数**——长度解析要是错了，这里就会是个错的扇区数，
> 一样看得见。**页 14 完全是新的、而且很关键**：卡上每张 640×480 24 位图都正好 `709` 个扇区,
> 所以"**多读了一张图**"在页 14 上就恰好表现为"多了 `70`"（4 KiB 单位；第一版按扇区显示时量程不够,
> 读回来是饱和的 `FFF`）。页 9~12 只能说明"读出来的是哪份字节",
> 说明不了"这份字节是第几张图"——那要靠页 14 和卡上的实际顺序对照。

> 页 13 是 2026-10-16 晚些时候加的，专门用来把"读通路"再切一刀：页 9~12 证明了**帧存里是这张图**，
> 但画面在屏幕上还是一块纯色。于是分别数"**进来的字**"和"**出去的像素**"的变化个数：
> 字在变、像素不变 → 故障在**字缓冲 → 字节移位**这一段（读侧）；字就已经不变 → 故障在**取数**
> （突发捕获 / 地址）。两个计数器各跑满一个窗口（或 0.25 秒）就停下，所以显示读到的值早就稳定，
> 跨时钟域直接读是安全的。

> 页 9~12 是 2026-10-16 新加的：等画面上了屏，自检探针用**单字端口**（这条路上没有
> 突发端口、也没有读通路的状态机）去**画面区**里取两个字并摊在数码管上。它回答的是
> 页 3 的 `0xFF` 计数**回答不了**的问题——"帧存里到底是这张图，还是任何一张非空白的图案"。
> 页 9/10 是第一个像素，页 11/12 是画面顶行第一个像素（也就是屏幕上第一行最左边那个像素），
> 两者各自 6 个 nibble：先 R,G,B 的高 4 位（页 9/11），再低 4 位（页 10/12）。
> 拿它和卡上第一张图的真实字节对一下就能定位：
>
> | 页 9/10、11/12 读到 | 结论 |
> |---|---|
> | 正是文件里那两个像素（见下表） | **帧存里就是这张图** → 问题在读通路/像素这一侧 |
> | 两页一样、而且都是 `FFF` | 帧存是空白（`0xFF` 一片）→ 写侧（加载器 → 打包 → 帧存）的问题 |
> | 两页一样、但不是空白 | 帧存是一块**纯色**→ 写侧的字节流卡住了（页 3 的 `0xFF` 计数看不出纯色！） |
> | 和自检图案有关（`A5A` / `55A` …） | 读回来的**根本不是画面区**，地址没译码对 |
> | 全 `000` | 那个地址上什么都没落过 |
>
> `bmp_out/` 里按文件名排序的第 1 张（`00_18c1b7…`，也是扫描最先遇到的那张）应该是
> **页 9/10 = `050` `50D`、页 11/12 = `030` `20A`**；若卡上第一张不是它，其他候选见下表：
>
> | 图 | 页 9/10 | 页 11/12 |
> |---|---|---|
> | `00_18c1b7…` | `050` `50D` | `030` `20A` |
> | `00_5a9a5f…` | `577` `FFB` | `FDF` `3FB` |
> | `01_345105…` | `5A4` `D3A` | `5C4` `F3C` |
> | `01_97a1af…` | `EAD` `8D9` | `FFF` `FFF` |
> | `02_44afe9…` | `FFF` `BFB` | `FFF` `FFF` |
> | `05_b0cc03…` | `FFF` `FFF` | `FFF` `FFF` |
> | `07_e75d63…` | `E5E` `DF1` | `F0F` `0F0` |

> 页 1 的 `709` 是**加载器真读到的扇区数**；**页 14** 才是"加载器实际去读的位置"（起始扇区低 12 位）。
> 两者配合才回答得了"读的是不是第一张图"——因为卡上每张图都是 `709` 个扇区，扇区数对而多读一张
> 在页 1 上看不出来，在页 14 上恰好差 `709`。
> 另外那个判断本身仍然成立：长度对、位置错的话，加载器照样能读满 921600 字节（它按字节数计数，
> 不会露馅），而内容是卡上的空白/旧数据 —— 那正好是"白屏"。

> **页 4/5/6 读的是原始值，不是"通过/不通过"**。这是刻意的：只有"失败"两个字，一次上板
> 只能否掉一个假设；原始值一次能否掉好几个 ——
> `A5A55A5A` 是对的、`5A5AA5A5` 是字节序反了、`00000000` 是没写进去或读成 0、
> `FFFFFFFF` 是数据总线悬空、**每次上电都不一样**则是裕量不够。
> 把三页连起来读成一个 8 位十六进制数即可。
>
> 页 6 的 d2 和页 7 的 d2 是**自校准**的结果：上电时探针把**八个采样码**各试一遍——
> 两组总线采样（0° 沿采 / 用 180° 时钟采一份副本）× 四个整周期偏移（`0` = 按原设计、
> `1` = 晚一拍、`2` = **早一拍**、`3` = 晚两拍；特意包含"早"的方向，因为"器件比假设更快
> 应答"和"永远不在窗口里"从外面看是一样的）。挑出能对上的那个并把编码**交给控制器**，
> 所以图像通路用的是标定过的节拍；**显示 `F` 说明八个码一个都没对上**。

> 页 3 的 `0xFF` 计数是判断"帧存里到底是真图还是空白"的最直接证据：真实照片前 255 个
> 像素字节里 `0xFF` 通常是个位数，**空白区则是 `FF`（255）**。配合错误码一起看：
> `0 FF` 表示"读得没错，但数据本身就是 `0xFF`"。

### 页 3 的 d3：加载器错误码

| d4 | 含义 |
|---|---|
| 0 | 没失败（正在加载或已加载完成） |
| 1 | 扇区读失败（重试 3 次后仍失败） |
| 2 | 表项为空 / 文件太短 |
| 3 | 文件太大（像素超过 `words_total` 能表示的范围） |
| 4 | **读到的扇区开头不是 `BM`** |

第 4 条是这次新加的**起始位置自检**：扫描是靠"扇区头两字节是 `BM`"认定这个文件合法并
记下它的起始扇区的，所以加载器读同一个扇区时**必须**看到同样的两个字节。不是就立刻报错、
一个字节也不交给帧写通路 —— 把"读到别的地方去了"从静默失败变成显式错误。

> 页 3 记的是加载器**真读**的扇区数，页 1 是扫描按文件长度**算出来**的扇区数。
> 两者应该一致（640×480 的图都是 `709`）——不一致就说明"长度解析"或"按长度读"
> 有一边错了，一眼能看出来。

### 页 4/5/6 与页 7：片内 SDRAM 自检

上电时（控制器就绪后）往存储空间最末尾写一个已知字 `A5A5_5A5A`，读回来，**把读回的
原始 32 位值摊在三页上显示**；然后往相邻器件行写四个"走位半字节"的字
（`A5A50001` / `A5A50010` / `A5A50100` / `A5A51000`），用**突发端口**（屏幕上真正走
的那条路）整段读回验证，结果放在页 7。

**这是判断"白屏/花屏到底是存储器不工作还是别的原因"的唯一直接证据**——控制器不校验
器件，器件没响应它照样报成功，所以上游一切"完成"都不能证明存储真的有效。探针占用的
地址在最后两个器件行，任何帧都不会用到。

> 曾经试过"扫四个采样点、挑能用的那个"来自校准。那个做法把 32 个触发器挂到了**驱动
> SDRAM 宏的那条 180° 时钟**上，板子上反而更糟（读数从"大部分字节对"变成"一个都不
> 对"）。现在裕量改由**把存储域降到 62.5 MHz** 来买，采样点固定用控制器自己的 0° 沿。

### 存储域为什么是 62.5 MHz

SDRAM 的数据在一个器件时钟周期内都有效，所以采样点到最近一次跳变的裕量约为**半个
周期**：125 MHz 是 4 ns，62.5 MHz 是 8 ns。带宽完全够——突发端口每拍一个字，62.5 MHz
就是 62.5 M 字/s，而 640×480@60 只需要约 13.8 M 字/s，写侧同理。HDMI 串化器仍然用
另一路 125 MHz 输出，**视频通路一点没动**。

### 页 3 的 d4：图片加载阶段码

| d4 | 含义 |
|---|---|
| 0 | 还没开始加载（扫描未完成，或卡里没有合法图片） |
| 1 | 正在逐扇区读图片文件 |
| 2 | 文件读完了，正在等写通路把最后几个字落进 SDRAM |
| 3 | **加载完成** ✓（画面已经切成图片） |
| F | 加载失败（读扇区出错 / 文件长度不对），每秒自动重试一次 |

> 页 1 那个数是可以对账的：`tools/prepare_images.py` 出的 640×480 24 位 BMP 是
> 921654 字节 = 1801 个扇区 = `709`（十六进制）。所以页 1 显示 `709` 就说明
> "文件长度解析正确"。超过 `FFF` 会饱和显示 `FFF`。

### 页 0 的 d4：存储阶段码

上电后先等 1 秒，再每 1 秒尝试一次；中途插入的卡也会被接上。某一轮读扇区或扫描
失败会先重试 3 次，仍然失败就把卡整个重新初始化一遍，如此循环，不会锁死。

| d4 | 含义 |
|---|---|
| 0 | 尚未开始（上电后头 1 秒） |
| 1 | 等待卡自身上电 |
| 2 | CMD0 复位到 idle |
| 3 | CMD8 探测卡版本与供电 |
| 5 | **ACMD41 轮询等待卡就绪**（卡刚上电时会在这里停留几轮） |
| 6 | CMD58 读 OCR |
| 7 | 初始化完成 ✓（接着马上开始读扇区） |
| 8 | CMD17 已发出，等卡回 R1 |
| 9 | 等数据令牌 0xFE / 正在收 512 字节 |
| A | **MBR 尾部签名 `55AA` 校验通过** ✓（紧接着开始扫描） |
| B | **正在扫描分区找图片**（写好的卡上通常一两秒就扫完） |
| C | **扫描完成** ✓（正常时稳定停在这里） |
| F | 失败（无卡 / 卡不响应 / 超时 / 签名不对 / 没扫到图），原因见 d2 |

> 序列里 CMD55（代码 4）是瞬态步骤，几十微秒就过去了，显示它只会让数码管闪烁，
> 所以跳过去不显示；8、9、A 三格在好卡上各只持续 0.2 ms 左右，基本是闪一下，
> 只有卡在"等数据"上卡住时才会停下来让你看见。所以 d4 的顺序是
> `0→1→2→3→5→6→7→8→9→A→B→C`。

### 页 2 的 d3 d2：容量

分区 1 的**容量**：十六进制 GiB，向上取整（`向上取整(扇区数 / 2^21)`）。
注意"标称容量"和"GiB"不是一回事：

| 卡的标称 | 分区大致 GiB | 数码管 |
|---|---|---|
| 8 GB | 7.4 | `08` |
| 16 GB | 14.9 | `0F` ← **2026-10-13 实测值** |
| 32 GB | 29.8 | `1E` |

> 各家卡的扇区数有百分之几的出入，所以上表是量级对照，不是精确换算表；
> 精确规则就是"向上取整(分区扇区数 / 2^21)"。

### 页 0 的 d2：错误码

| d2 | 含义 |
|---|---|
| 0 | 最近一次没有失败 |
| 1 | CMD17 发出去后卡一直不回 R1（等满 100000 个 0xFF 字节） |
| 2 | 卡回了 R1，但带错误位（卡拒绝了这次读） |
| 3 | 卡一直不给数据令牌 0xFE（等满 400000 个 0xFF 字节） |
| 4 | 卡回了数据错误令牌 0x0X，说明这个扇区它自己读不出来 |
| 5 | 扇区读回来了，但尾部不是 `55 AA`（不是 MBR 分区表） |
| 6 | 扫描跑完了，但整个分区里没有一个合法图片文件 |
| 7 | 卡初始化失败（没插卡 / 卡不响应 / ACMD41 一直不就绪） |

> 万一卡是"超级软盘"格式（没有 MBR 分区表），扇区 510/511 依然是 `55AA`，
> 但偏移 450 处的分区类型是 0，此时容量页显示 `A 00`：读通了，只是没有可解析的
> 分区容量；扫描仍然会从第 0 扇区开始找图。

### 卡怎么准备

图片必须用 `tools/write_card.py` 顺序写进卡：FPGA 不解析文件系统，它是**逐个扇区
看每个扇区的头两个字节是不是 `BM`**，再校验 BMP 头（640×480、24 位、非压缩、
像素数据偏移 54、长度覆盖像素）。所以手动往卡里拖图片、或者手动删图片都不行——
旧的物理数据留在扇区里一样会被扫到。写卡流程见 `doc/TF卡文件格式.md` 第 5 节。

```
python tools/write_card.py --no-audio --dry-run   # 先看计划
python tools/write_card.py --no-audio             # 确认后真写，会让你输 yes
```

盘符不用写：本项目这台机器的 TF 卡固定是 `G:`，不写就用它，工具还会打印卡容量
（"共 15.9 GB"）让你确认没点错设备；写别的盘符会警告。双击运行只会打印用法，
不会碰卡。

**写卡会清空整只卷**，所以工具加了盘符安全闸：只肯写"盘符是本机固定的 `G:` **且**
容量 ≤ 64 GB"的卷。只要有一条不满足（例如手滑把 `E:`——那是一块 300 GB 的数据盘
——填进去），它直接拒绝，**`--yes` 也绕不过**，必须显式加 `--force-drive`。

扫描的几个边界：从 MBR 给的分区起始 LBA 开始；连续 16 MB 没找到新图片就停；
总预算 100 MB；最多记 8 张。找到一张图后按它头部声明的长度直接跳过去，
所以正常有 8 张图的卡上一两秒就扫完；音轨（`MMAU`）也会按头部长度跳过，
免得逐扇区爬过去。

> **上电时 d4 会在 `b` 停几秒**（2026-10-13 实测约 5 秒，当时卡里只有 2 张图）：
> 找到最后一张图之后，扫描要继续爬满 16 MB 空白区才敢说"没有更多图了"。
> 写满 8 张时表格一满就停，这一段几乎看不到。**这是上电扫描的一次性开销，
> 不是卡住，也不是在反复重试**——修复前的症状是它在 `C` 和 `b` 之间无限循环。

按 **KEY1（引脚 A2）**：复位。屏幕黑一下再恢复，两个跳动位重新从 0 开始，SD 也
从初始化重来。

已知现象：图像在显示器上整体偏右下约 1 像素，上边框看不到（原因见
`doc/HDMI协议笔记.md` 第 3 节，不影响功能）。
